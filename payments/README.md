# بوابة الدفع — Moyasar

## كيف تعمل (بدون ما تلمس بيانات بطاقة أبداً)

1. المستخدم يختار باقة → `POST /api/payments/create-invoice` ينشئ فاتورة بحالة `pending` بقاعدة البيانات، ويطلب من Moyasar صفحة دفع جاهزة (`checkoutUrl`).
2. توجّه المستخدم لـ`checkoutUrl` — **يدفع على صفحة Moyasar نفسها**، بطاقته ما توصل خادمنا إطلاقاً. هذا يخليك خارج نطاق PCI-DSS تماماً، عكس لو بنينا نموذج بطاقة بأنفسنا.
3. بعد الدفع، Moyasar يرسل webhook حقيقي لـ`POST /api/payments/webhook` — **وهذا المكان الوحيد اللي يفعّل الاشتراك فعلياً**، مو صفحة النجاح اللي يرجع لها المستخدم (لأن أي حد يقدر يفتح رابط النجاح يدوياً بدون ما يكون دفع فعلاً).

## ⚠️ نقطة تحقّق مهمة اكتشفتها بالبحث — مو افتراض

بحثت بتوثيق Moyasar الرسمي قبل ما أكتب أي كود، ولقيت شي يخالف الافتراض الشائع لبوابات الدفع: **Moyasar ما تستخدم توقيع HMAC للـwebhooks**. بدلها، تحط `secret_token` مباشرة جوه جسم الرسالة JSON، وأنت تقارنه بالسر اللي حددته وقت تسجيل الـwebhook. لو كنت بنيت تحقق HMAC (الافتراض الشائع)، كان ما يشتغل إطلاقاً مع Moyasar الفعلية.

## خطوات الإعداد

**1. جهّز حساب Moyasar:** [dashboard.moyasar.com](https://dashboard.moyasar.com) → Developers → API Keys. ابدأ بمفتاح `sk_test_...`.

**2. عبّي `.env`:**
```
PAYMENT_SECRET_KEY=sk_test_...
PAYMENT_WEBHOOK_SECRET=<ولّد: openssl rand -hex 24>
APP_BASE_URL=https://yourdomain.com
SERVER_BASE_URL=https://yourdomain.com
```

**3. سجّل الـwebhook مرة وحدة (بعد ما يشتغل السيرفر بنطاقك الحقيقي):**
```bash
node payments/register_webhook.js https://yourdomain.com/api/payments/webhook
```

**4. جرّب بمفتاح test أول** — بطاقات اختبار جاهزة موجودة بتوثيق Moyasar (`docs.moyasar.com`)، قبل ما تنتقل لمفتاح `sk_live_`.

## ما تحقق فعلياً (شغّلت الأوامر بنفسي، مو افتراضاً)

- ✅ webhook برمز سري خاطئ → **مرفوض فعلياً (401)**.
- ✅ webhook بدون `secret_token` إطلاقاً → **مرفوض فعلياً (401)**.
- ✅ webhook برمز سري صحيح لكن فاتورة غير معروفة → **مقبول (200) بدون ما يكسر أي شي**، مسجَّل بالسجل كـ"غير مطابق" بدل ما يفشل السيرفر.
- ✅ إنشاء فاتورة بمفتاح Moyasar وهمي → **فشل بشكل صحيح (500)**، والأهم: **تحققت إن سجل الفاتورة المعلّقة (pending) اتسجّل فعلياً بقاعدة البيانات قبل ما نداء Moyasar يفشل** — يعني حتى لو انقطع الاتصال بـMoyasar، عندك سجل دائم تقدر تتابعه.
- ✅ طلب برقم باقة غير موجود → **مرفوض قبل ما يلمس قاعدة البيانات أو Moyasar إطلاقاً**.
- ✅ السيرفر ما وقع بأي من هذي الحالات.

## ⚠️ فجوة حقيقية لازم تُحل قبل التشغيل الفعلي

**`POST /api/payments/create-invoice` حالياً يثق بـ`userId` يجيه من الطلب مباشرة، بدون أي تحقق هوية حقيقي** — لأن `marsa-server` ما عنده نظام تسجيل دخول حقيقي للمستخدمين العاديين بعد (بس الإدارة عندها، اللي بنيناها بالجلسة السابقة). حالياً أي شخص يقدر يدّعي إنه أي `userId` ويطلب فاتورة باسمه.

**لا تنشر هذا الـendpoint للعموم قبل ما تبني تسجيل دخول حقيقي للمستخدمين العاديين** (تسجيل + كلمة مرور + جلسة حقيقية، بنفس نمط `admin/auth.js` اللي بنيناه للوحة التحكم). لما يصير عندك هذا، أضف middleware تحقق هوية هنا بنفس طريقة `requireAdminAuth`.

## فجوة ثانية — تنسيق الأسعار (تحديث: نصف الفجوة انحلّت)

أسعار الباقات كانت **مكتوبة مباشرة بالكود** (`PLANS` بـ`payments/routes.js`)، منفصلة تماماً عن مصفوفة `plans` الموجودة بالتطبيق الأمامي (`wellness-companion.jsx`). **هذا الجزء انحلّ**: الأسعار الآن بجدول حقيقي (`subscription_plans`)، تُدار من صفحة "الاشتراكات والباقات" بلوحة التحكم، ويقرأها الخادم فعلياً وقت الدفع — مو نسخة ثابتة بالكود.

**الجزء الباقي فعلاً:** أضفت `GET /api/payments/plans` (endpoint عام بدون مصادقة) خصيصاً عشان التطبيق الأمامي يستدعيه بدل ما يكرر قائمة أسعار خاصة فيه — **لكن `wellness-companion.jsx` لسا ما يستدعيه**، لسا يستخدم مصفوفة `plans` الثابتة بداخله. يعني لو غيّرت سعر من اللوحة الحين، الخادم يتحدث فوراً (مؤكد، اختبرته)، لكن **واجهة المستخدم القديمة ما تعرض السعر الجديد إلا لو ربطناها بالـendpoint الجديد**. هذا العمل التالي المنطقي، لسا ما تم.
